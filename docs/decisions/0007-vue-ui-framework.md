# ADR 0007：Vue 裁判端 UI 框架

- 状态：已接受
- 日期：2026-11-02

## 背景

裁判端是 Vue 3 + TypeScript + Vite 的移动优先静态 SPA。当前工作台已有自定义按钮、弹窗、提示、数字输入和卡片样式；继续手写这些基础交互会重复实现键盘焦点、禁用态、模态层语义、触控尺寸和主题状态。

项目需要：

- 适配 Vue 3 与 TypeScript，并能以静态资源部署；
- 覆盖按钮、卡片、Modal、Alert、InputNumber、Empty 等常用基础组件；
- 支持通过 design token 还原项目规定的 FIBA 暖沙金、炭黑和球场红，而不是引入另一套品牌视觉；
- 保持移动端触控目标和弱网/离线场景下的低运行负担；
- 尽量按需导入，避免为一个工作台引入完整应用框架运行时。

## 决策

采用 **Naive UI 2.x** 作为裁判端的基础 UI 组件库。本次接入使用 `NConfigProvider` 的 `GlobalThemeOverrides` 统一映射 FIBA 设计 token，并将工作台的基础按钮、卡片、提示、弹窗、数字输入和空状态迁移到 Naive UI。比赛计时领域逻辑、布局编排和产品特有的计时面板仍由应用代码负责；UI 框架不替代领域模型。

Naive UI 的组件使用 TypeScript 编写，支持 Vue 3、主题覆盖和按组件导入；其组件可通过现有 Vite 构建为静态资源，不需要生产期 Node.js 服务。

## 方案比较

- **Element Plus**：组件覆盖和文档成熟，但默认更偏桌面后台，主题改造需要额外 Sass/按需导入配置；对当前轻量移动工作台会带来较多不必要的基础样式与配置。
- **PrimeVue**：组件和主题能力强，但 v4 styled mode 需要额外主题 preset 依赖，且视觉基线更接近通用企业组件；对于本项目已有的严格 FIBA token，集成层次较重。
- **Quasar**：适合同时覆盖移动、桌面和 PWA 的完整框架，但会把路由、构建、平台能力等更多约束带入当前静态 SPA；项目当前仅需要 UI 组件库而非全栈应用框架。
- **Naive UI**：Vue 3 原生、TypeScript 友好、主题覆盖直接使用 TS token，无需 Sass 主题管线；组件覆盖满足当前工作台且可按组件导入，符合低基础设施负担要求。

## 后果

- 基础交互组件不再重复手写语义、状态和主题实现；应用仍需为场边计时布局和领域操作提供专用代码。
- Naive UI 的主题覆盖必须集中维护，禁止在单个页面重新定义一套颜色或圆角体系。
- 组件升级需要关注 Naive UI 2.x 的 API 兼容性，并在 `typecheck`、单测和生产构建中验证。
- 当前不引入全局自动组件扫描插件，先采用显式组件导入，保持依赖边界和产物可见；组件数量增长后再基于构建测量决定是否采用自动按需导入。
