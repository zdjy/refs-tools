# ADR 0038：正式成员名单读取与成员管理分离

- 状态：已接受
- 范围：[FS-0027 §18](../specs/0027-referee-organizations.md#18-所有正式成员可查看成员名单)
- 补充：[ADR 0028](0028-organization-members-and-invitations.md)、[ADR 0032](0032-referee-organization-access.md)；联系方式仍遵循 [ADR 0035](0035-member-contact-projection.md)。

## 背景

用户端将成员标签与名单接口均绑定到管理权限，普通成员与认证员无法了解本组织成员。此次需求要求所有组织角色均可查看名单，但不应同时扩大联络资料、入会审核和历史关系的可见范围。

## 决策

1. 本组织正式成员可读取本组织正式名单，不要求额外组织角色；以实时 `active` 成员关系为依据，待审核、退出、移除及跨组织关系不授予读取权。冻结或解散组织中的既有正式成员仍可只读名单，不因此恢复运营权限。
2. 复用现有名单接口与分页契约。Service 在组织行锁和同一事务内读取账号及成员关系，向 Repository 传入仅服务端控制的 `activeOnly`。计数、关键词过滤与分页共用状态条件，不能取全量后在前端过滤。
3. 组织管理者继续读取申请与历史关系；平台非成员审计账号保留既有治理读取。平台账号若本身是该组织正式成员但无组织管理能力，按普通成员名单范围读取，不因角色混合扩大客户端投影。
4. `canManage` 含义不变，由现有单一权限矩阵计算；邀请读取、联系方式和成员写入继续独立授权。前端只读名单没有联系资料入口及管理动作，不将隐藏按钮当作安全边界。
5. 所有成功名单读取继续与 `membership.queried` 审计同事务。私有名单不新增持久化或离线缓存。

## 备选方案与后果

- 只显示标签、不改 API：进入后仍被拒绝，不能满足需求。
- 向所有成员授予 `organization.members.manage`：会连带开放审核、移除与联系方式，拒绝。
- 向所有成员开放完整历史名单：扩散待审核及离会记录，超出查看当前成员的目的，拒绝。
- 新建重复名单端点：当前载荷与查询条件可复用，无需新增端点、迁移、依赖或基础设施。
