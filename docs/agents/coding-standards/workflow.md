# AI 开发执行协议与自检清单

本文件属于[全栈架构与编码规约](../coding-standards.md)。

当指派给 AI 任何新的开发或修复任务时，AI **必须按以下步骤逐步生成代码，禁止单次全量揉合生成**：

## 1. 标准执行顺序（5 步工作流）

1. **Step 1 - 契约先行**：优先在 `packages/contracts` 中声明 TypeBox Schema 与 TypeScript DTO 接口。若涉及核心业务规则（如资格打分、时间冲突判定），在 `packages/domain` 中编写纯函数并补全单元测试。

2. **Step 2 - 数据库持久层**：先在所属模块 `*.types.ts` 定义无驱动依赖的 Repository 契约，再在 `*.repository.ts` 实现 SQL 与行映射；按需新增迁移。涉及事务时复用应用事务端口与数据库适配器，由装配入口注入依赖，不把 `pg` 类型传入 Service。

3. **Step 3 - 业务编排层**：在 `apps/api/src/modules/<feature>/<feature>.service.ts` 中组装流程、规则校验及异常抛出。

4. **Step 4 - 路由接入层**：在 `apps/api/src/modules/<feature>/<feature>.routes.ts` 挂载端点并指定 schema 校验。

5. **Step 5 - 前端组件化交付**：按需在 `apps/referee-web/src/api/` 写入 API 映射，在对应 `views/<feature>/` 下拆分 `use<Feature>.ts` 与单视图组件。按[前端规约](frontend.md#3-ui-组件框架与-ddd-边界)的边界接入 Naive UI，先复用集中主题与既有组件，仅将确有通用需求的封装放入 `components/ui/`；完成相关交互与构建检查。

仅涉及 UI 或数据库基础设施的任务不必机械新增跨端契约、领域模型或后端五文件；先确认是否改变业务规则或跨端载荷，再执行实际涉及的步骤。

## 2. 交付前自检清单（必须逐条通过）

* \[ \] 后端是否有任何业务 SQL 写在了 `routes.ts` 或 `service.ts` 中？业务查询须在 Repository，连接/迁移 SQL 须在数据库基础设施。

* \[ \] Repository 契约与事务端口是否无驱动依赖，Service 是否只依赖端口且由入口注入？`pg`、SQL 和行类型是否未泄漏至 contracts/domain、Service 或路由？

* \[ \] 事务内 Repository 是否共用同一连接、未逃逸回调且无外部 IO？提交/回滚/释放与回滚失败销毁是否有测试，审计/outbox 是否满足规格的一致性要求？

* \[ \] 业务表是否有明确模块所有者，领域不变量是否有数据库约束及并发策略兜底？行映射、最小投影、参数化查询与错误分类是否明确，迁移及相关真实 PostgreSQL 检查是否已执行？

* \[ \] 单个 `.vue` 文件总行数是否超过[前端规约](frontend.md#2-前端硬性约束)规定的统一上限？（如超过，必须拆分子组件）

* \[ \] 前端 `.vue` 的 `<script setup>` 中是否含有直接的 HTTP 请求？（如有，必须抽至 `api/*.ts`）

* \[ \] 跨端传输的数据接口是否在 `packages/contracts` 中统一定义？

* \[ \] 每一个新建的 `domain` 规则和 `service` 是否包含配套的 Vitest 单元测试？

* \[ \] 涉及授权时，第三方引擎是否仅由 API 适配器经端口注入，固定策略是否单一来源，且无用户角色图/决策缓存、跨绑定拼接或异常回退放行？是否验证实时撤权、请求隔离及同事务授权/审计？

* \[ \] Naive UI 是否只被表现层/主题适配使用，未进入 `contracts`、领域模块、API 或业务 Composable？组件库类型是否留在表现层？

* \[ \] 组件封装是否确有通用需求且不包含业务逻辑？业务组件是否仍归属对应模块，无跨应用/跨页面目录引用？

* \[ \] 主题是否集中维护并符合共享 UI 规范，无逐页重复 token、全量组件注册或未说明的内部样式覆盖？

* \[ \] 表单交互校验、领域不变量与 API 授权是否各归其位？加载、错误、离线、重试及破坏性操作确认是否符合相关规格？

* \[ \] 状态是否按领域、应用用例、界面状态分层？Pinia 是否仅拥有明确需要共享的应用状态，且无隐式持久化、网络或 UI 框架耦合？

* \[ \] Router 是否只承担静态 URL 到视图/用例输入的映射与导航体验？守卫是否未承担领域规则或 API 授权，业务状态层是否未依赖 Router 实例？

* \[ \] 涉及 UI 时，是否检查移动端触控、键盘/焦点、可访问名称、reduced-motion 与主题状态，并执行相关单测、`typecheck` 和生产构建？未涉及项标明不适用，无法执行的检查须说明原因。

* \[ \] 注释是否解释意图而非复述代码？是否存在注释掉的死代码、无 issue 的 `TODO`、粘贴的规格段落，或用注释代替校验、授权、离线与可访问性实现？

* \[ \] 领域函数、契约字段与复杂 SQL 的规则依据、单位与边界是否已在注释中说明，且与 `docs/specs/` 及规则集配置一致？

* \[ \] 新增与迁移的界面是否按[样式规约](styles.md)使用 Tailwind CSS？配置与扫描是否限定在所属前端应用，手写 CSS 是否仅为保留的基线或有说明的必要例外，未新增自制工具类或整页纯 CSS？

* \[ \] Tailwind 是否消费同一 token、使用项目统一断点，类名是否可静态扫描且无冲突？是否未用默认品牌色、硬编码主题值、important 修饰符或深层选择器绕过 Naive UI 主题，并在迁移时清理对应旧声明？

* \[ \] 样式接入或迁移是否验证了生产工具类生成与产物体积？涉及组件迁移时是否另做移动端、键盘/焦点、状态与 reduced-motion 浏览器验收，且未把仅完成构建接入表述为已完成全部 CSS 迁移？
